## Allowed scope

Give the reel a real editable document: a validated immutable project with
stable identities, an asset table with ownership rules, and an undo/redo history
that restores documents exactly. Wire the existing capture flow to it so there is
one source of truth rather than two lists.

**Included**

- `MediaAsset`, `ReelClipInstance`, `ReelCanvas`, `ReelProject` with validation
  on construction, integer-microsecond boundaries, and half-open `[in, out)`
  source intervals.
- Atomic commands (`AppendClipCommand`, `RemoveClipCommand`) that either produce
  a complete valid project or reject the edit with the project untouched.
- Bounded snapshot history with undo, redo, and redo-clearing on a new edit.
- Asset retention across every reachable revision, and a `releasableAssetIds`
  report that deletes nothing.
- Versioned serialization (`schemaVersion`, round-trip, newer-schema rejection).
- Capture integration: finalized takes commit as project clips; `ReelClip` becomes
  a derived view; capture's "remove last" is an undoable project edit.
- **The canvas-ownership fix** from the F00 audit.

**Explicitly excluded**

- Any editor UI. Undo/redo has no on-screen surface yet; the capture screen's
  existing Undo button keeps its current label and behavior (remove last clip).
  Exposing project undo/redo belongs to the timeline feature (F03).
- Timeline, filmstrip, selection, playhead (F03); trim (F04); split (F05);
  reorder (F06); arbitrary removal UI (F07); import (F08/F09); replace (F10);
  re-record (F11); crop editing (F12); canvas *changing* (F13); covers (F14).
- Writing drafts to disk. Serialization exists so a draft can be written later;
  **no persistence, no autosave, no recovery** is implemented. That is F15.
- Any render-path change. The FFmpeg preview/export path is untouched apart from
  reading the canvas from project state.
- Media probing. `MediaAsset` deliberately carries no pixel dimensions or
  audio-track details, because F00 found `VideoProcessor._probe` fabricates
  `1080x1920 @ 20 Mbps` on parse failure. A feature that genuinely needs those
  facts must probe honestly first.
- Motion, speed, layers, masks, text, and anything music-related.

## The canvas fix

F00 recorded that `_review()` passed `ratio: _session.clips.first.ratio`, deriving
the output canvas from whichever clip was first **at render time**. Reordering or
removing the first clip would have silently reshaped the reel the moment F06 or
F07 landed.

The canvas is now project state. The first accepted clip initializes
`ReelCanvas`, and nothing in this feature can change it afterwards:

- A later clip with a different ratio does not change it.
- Removing the clip that set it does not change it — `originClipId` is kept for
  provenance only.
- Emptying the sequence entirely keeps the established canvas.
- `_review()` reads `project.canvas.ratio`, not the first clip.

Deliberate project-wide canvas changes are F13's feature; there is no command to
change the canvas yet, by design.

## Asset ownership

Removing a clip does not remove its asset from the project's asset table, and
never deletes a file. An asset is retained while **any** reachable revision
(undo stack, current document, or redo stack) references it, so undo can always
bring the clip back with its media intact.

`releasableAssetIds` reports assets no reachable revision needs — typically
because the history step that used them fell off the bounded undo stack. It is a
report only. File cleanup, the discard flow, and their ownership rules belong to
F15.

## Build identity

**No APK.** Same blocker as F00: the container has no Android SDK, and
`dl.google.com` is denied by the environment's network policy, so neither the
command-line tools nor the AGP 9.1.0 artifacts can be fetched. `adb` is absent
and no USB bus is exposed, so the attached phone is not reachable from here. No
signing or release setting was altered.

## Real-device checklist

F01 changes behavior in one observable way (the canvas source) and otherwise must
be invisible. Build from this branch on a machine with the Android SDK, then:

### Capture regression — must be unchanged

| Action | Expected |
| --- | --- |
| Hold-record three clips | Appends in order; next clip only after the previous finalizes |
| Hands-free 3 s / 5 s / 30 s / custom 1–300 s | Unchanged; timer starts at actual recording start |
| Tap Undo after several clips | Removes exactly the most recent clip |
| Tap Undo until empty, then record again | Works; no stale clip reappears |
| Switch front/back between clips | Front clips still mirrored in the output |
| Background mid-recording, return | Earlier clips survive; camera reopens |
| Deny the microphone, record | Still records; clip contributes silence |

### Canvas ownership — the new behavior

| Action | Expected |
| --- | --- |
| Record clip 1 at **1:1**, clip 2 at **9:16**, preview | Output canvas is **1:1** (set by clip 1). Clip 2 is letterboxed inside it |
| Record clip 1 at **16:9**, clip 2 at **1:1**, preview | Output canvas is **16:9** |
| Record 1:1 then 9:16, tap Undo (removing clip 2), record a 16:9 clip, preview | Canvas is **still 1:1** — it must not follow the newest or the first remaining clip |
| Record 1:1, Undo it, record 9:16, preview | Canvas is **1:1**, established by the first accepted clip of the session |

The last two rows are the regression this feature exists to prevent. Before F01
the canvas was recomputed from whichever clip was first at render time.

## Limitations

- **Device verification has not run.** Every result above is host-side
  `flutter analyze` and `flutter test`. Nothing in this feature has been observed
  on the Realme V7 Max or any other device, and no APK exists.
- Undo/redo is reachable from code and tests only. There is no button for it
  until F03 builds the editor, so a device test of project undo/redo beyond
  capture's remove-last is not possible yet.
- The project is in memory only. Killing the app still loses it, exactly as
  `docs/reels.md` documents. F15 changes that.
- `MediaAsset` has no pixel dimensions or audio-track facts; the render path
  still probes files itself through `VideoProcessor`.
- `historyLimit` defaults to 50 snapshots. That is a safe starting value, not a
  measured budget; F33 owns measuring it.
- `docs/reels.md` is unchanged, because no user-visible documented behavior
  changed. The canvas rule it already states ("The first clip sets the output
  canvas") is now actually true in code.
